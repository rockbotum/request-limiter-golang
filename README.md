# request-limiter-golang

Пять реализаций rate limiter на Go в одном репозитории. Задача - просто сравнить работу разных паттернов написания ограничителей.

У всех реализаций одинаковый публичный API, поэтому их можно подставлять друг
в друга:

```go
NewXxxLimiter(ctx context.Context, limit int, interval time.Duration) *XxxLimiter
func (l *XxxLimiter) Allow() bool
```

`limit` - сколько запросов разрешено за `interval`, `Allow` неблокирующий:
возвращает `false`, если запрос не проходит. `leaky-bucket` дополнительно
предоставляет `Wait(ctx) error` - единственный метод, который заставляет
вызывающего ждать своей очереди; на этом и строится его отличие от
`token-bucket`.

## Быстрый старт

```bash
go test ./...          # 94 теста, ~13 секунд
go test -cover ./...   # полное покрытие statement во всех реализациях
go test -race ./...    # проверка конкуренции, требует C-компилятора
```

Нужен Go 1.27.1 или новее (см. `go.mod`).

## Что где лежит

| Пакет в `implementations/` | Алгоритм | Фоновая горутина | Свойства |
|---|---|---|---|
| `fixed-window` | Счётчик запросов, обнуляемый по таймеру | да, сбрасывает счётчик | Самый простой, но допускает всплеск вдвое больше лимита на стыке окон |
| `sliding-window` | Взвешенный учёт двух перекрывающихся окон | нет | Плавный, без всплесков, O(1) памяти |
| `token-bucket` | Ведро токенов, пополняется каждые `interval / limit` | да, возвращает токен | Разрешает всплеск до `limit`, дальше ровно по одному токену |
| `leaky-bucket` | Очередь, из которой запросы выходят по одной через равные промежутки | да, выпускает по одному запросу за `interval / limit` | Единственный, кто реально задерживает вызывающего: см. `Wait` ниже |
| `sliding-log` | Журнал времён каждого запроса | нет | Самый точный, но память O(limit) и работа с логом линейная |

`internal/limitertest` - общий тестовый харнесс (об этом ниже).

## Что стоит знать

**`leaky-bucket` - единственный из пяти, кто действительно сглаживает поток, и
для этого у него есть второй метод.** Запросы складываются в очередь ёмкости
`limit`, а фоновый тикер выпускает по одному за `interval / limit`. Два правила
делают выход равномерным: запрос выпускается только по тику (ни раньше, даже если
в очереди есть место), а тик, заставший пустую очередь, выбрасывается, а не
копятся. Из-за этого алгоритм принципиально отличается от `token-bucket`, который
выдаёт разрешение сразу и копит неиспользованные токены: после получаса простоя
`token-bucket` пропустит сразу всю полную пачку, а `leaky-bucket` - только по
одному запросу за такт.

`Allow` здесь отвечает на вопрос «влезает ли запрос в ведро» и занимает слот до
тика, но сам вызывающего не тормозит. Задержку видно только через
`Wait(ctx) error`, который кладёт запрос в очередь и блокируется до его
выпуска; на полном ведре `Wait` не отказывает, а ждёт свободного слота.
`Len()` показывает текущую глубину очереди.

**`sliding-window` покрыт на 96.8 %, а не на 100 %:** в нём остался метод
`Start(ctx)`, который только блокируется на `ctx.Done()`. Его никто не вызывает
- конструктор его не запускает, в отличие от `token-bucket` и `leaky-bucket`, -
так что это мёртвый код. У `sliding-log` такого метода нет вовсе.

**Окна `fixed-window` отсчитываются от момента создания лимитера**, а не от
границ часов. На стыке окон пачка «до» и пачка «после» проходят вместе: при
лимите 4 это 8 запросов за 70 мс. Классическая проблема алгоритма, а не ошибка
реализации; `TestFixedWindowAlignsWindowsToConstructionTime` фиксирует это
поведение.

**`sliding-window` при переходе ровно на одно окно переносит счётчик текущего
окна в предыдущее целиком и тает его линейно от момента перехода.** Это
приближение игнорирует, что запросы могли прийти в разные моменты окна;
погрешность составляет доли запроса. Если простоя дольше одного интервала не
было, счётчик обнуляется полностью.

**`sliding-log` вытесняет старые записи лениво** - внутри `Allow`, а не по
таймеру. Между запросами в логе могут лежать записи, которые уже вне окна; они
не мешают, потому что проверяются при следующем вызове.

**`sliding-log` и `sliding-window` не запускают фоновых горутин**, поэтому
параметр `ctx` в их конструкторах не используется. Сигнатуры оставлены едиными
ради сравнимости; `NewXxxLimiter(context.Background(), ...)` - корректный вызов.

**`limit` и `interval` должны быть положительными**, иначе конструктор паникует с
сообщением, называющим виновный параметр. Раньше нулевые значения приводили к
панике внутри `time.NewTicker` уже после успешного возврата из конструктора, то
если в чужой горутине, и перехватить её на стороне вызывающего было нельзя.

## Тесты

94 теста, из них 21 - self-тесты самого харнесса.

Общий харнесс в `internal/limitertest` позволяет описывать сценарий как
virtualный таймлайн - набор пачек запросов с виртуальными смещениями, - а
`Replay` проигрывает эти смещения против реальных часов. Благодаря этому
сценарии, завязанные на границы окон («пачка прямо перед переходом окна и пачка
сразу после»), пишутся без россыпи `time.Sleep` и воспроизводятся одинаково:

```go
res := limitertest.Replay(t, limitertest.NewVirtualClock(1), limiter, []limitertest.Event{
    limitertest.Burst(250*time.Millisecond, 4),  // за 50 мс до стыка окон
    limitertest.Burst(320*time.Millisecond, 4),  // через 20 мс после стыка
})
limitertest.EqualInt(t, res.Window(240*time.Millisecond, 320*time.Millisecond).Allowed, 8,
    "allowed across a single boundary")
```

В харнессе есть ещё `ConcurrentBurst` для проверки под конкуренцией, `Steady`
для равномерной нагрузки, `Construct` - для проверки, что конструктор вообще
возвращается, и `ExpectPanicContaining` - для проверки сообщений паник.

Проверки конкуренции написаны так, что их стоит гонять с `-race`. В текущем
окружении это невозможно: `-race` требует cgo, а C-компилятора в системе нет.

## Структура

```
implementations/
  fixed-window-request-limiter/     fixed window
  leaky-bucket-request-limiter/     leaky bucket (очередь + Wait)
  sliding-log-request-limiter/      sliding log
  sliding-window-request-limiter/   sliding window
  token-bucket-request-limiter/     token bucket
internal/
  limitertest/                      общий тестовый харнесс
testdata/
```

В каждом пакете реализации два файла тестов: `request_limiter_test.go` с
проверками через публичный API и `request_limiter_internal_test.go` с проверками
внутренних счётчиков - там, где поведение нельзя увидеть снаружи.
